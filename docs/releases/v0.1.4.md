# Governed Agent v0.1.4

Status: release candidate; publication requires Jeremy's approval. No publication date is assigned.

This patch release prepares the execution and state-handling fixes merged in [PR #2](https://github.com/jtevesnz-sys/governed-agent/pull/2), merge commit `28f365ae4c2cb21dd994fdeead269795b890f159`. It also aligns package metadata, the imported package version and the planning server's reported version at `0.1.4`.

## Changes

- Consume verified tool receipts atomically in a shared SQLite database before dispatch. Reuse is denied across cooperating boundaries, concurrent calls and process restarts. Failed tools and interrupted execution retain the consumption record; replay-store failure denies execution.
- Freeze native receipt bytes before signature verification, request matching and replay hashing, preventing mutable buffers or overridden conversion methods from substituting requests.
- Lock and reload file-backed authority state across cooperating Windows and POSIX processes. Stale instances cannot reverse sequence progress, and invalid pins are rejected before storage changes.
- Reject malformed receipts and manifests through controlled verification results. Nested context comparison preserves JSON scalar types, so `true`, `1` and `1.0` differ. Oversized JSON integers and artifact-path loops are handled without turning recognized malformed input into an uncaught error.
- Bind state paths once at construction. Configured paths do not require a home directory, and changing a tool's working directory does not redirect relative state paths.
- Add development history and a bounded maintenance case study, and extend CI to Windows Python 3.12 alongside Linux Python 3.10–3.13.
- Include the changelog, release documentation and test-isolation fixture in the source distribution so tests run from that archive retain their isolated state configuration.

## Upgrade requirements

1. Choose one protected replay database for each execution domain and configure every participating boundary to share it. Use `replay_store_path` or `GOVERNED_AGENT_REPLAY_STORE_PATH`; the default is `~/.governed_agent/receipt_replay.sqlite3`. The storage must support SQLite locking and durable commits. Separate databases do not share replay evidence.
2. Preserve the replay database, authority key, pin/counter history and lock file. Deleting or restoring old state can remove replay evidence. Receipt consumption starts with this version; it cannot reconstruct actions previously executed without a consumption record.
3. Treat tool failures and interruptions as consumed authorization. A crash after consumption can prevent dispatch, and a failing tool can already have side effects. Check the operation's actual outcome before obtaining a separately approved replacement receipt. This is at-most-once authorization, not exactly-once tool completion.
4. Expect stricter input rejection. Correct malformed payloads, duplicate receipt keys, non-finite context values or JSON type mismatches instead of bypassing verification.
5. If an existing authority has a key but missing or inconsistent state, restore its matching history. An owner may instead approve a new authority in a separate directory. Do not delete the existing key or reset its history to make initialization pass.

No automatic state reset, receipt refund or history cleanup is introduced. No additional third-party runtime dependency is added.

## Verification and limits

The merged implementation passed 234 tests on Windows/Python 3.12, with one real symlink-loop fixture skipped because the account lacked symlink privileges. Statement coverage was 92%. Linux/Python 3.12 passed all 235 tests, including the real loop, with 91% statement coverage. The PR's Linux Python 3.10–3.13 and Windows Python 3.12 CI jobs passed. Its final automated review produced no actionable findings, and all four review conversations were resolved.

Release preparation additionally checks both distribution formats, their metadata, installed versions and planning-server responses. Exact candidate revision, package hashes and final check results are retained in the release-preparation receipt before approval.

This remains a reference implementation, not a comprehensive security audit or production qualification. Replay protection depends on retained shared state. Authority locks coordinate cooperating writers; pin/counter file replacements are individually atomic and inconsistent interrupted pairs are rejected. Replaying a complete older authority snapshot, signing-key custody, trusted manifest provenance and enforced auditor isolation remain separate concerns.

## Publication boundary

The proposed tag is `v0.1.4`. Preparation creates neither that tag nor a GitHub/PyPI release. After owner approval, the version-preparation change must be merged and the exact approved commit verified before tagging. Publishing a GitHub release triggers the existing PyPI workflow, which tests, builds and validates distributions and requires the tag to match the package version. PyPI publishing permissions and environment approval remain subject to the live workflow; preparing this candidate does not prove that publication will succeed.

If a distribution needs correction, preserve its records and publish an approved follow-up version rather than replacing an existing release file. Preserve replay and authority history through any code rollback; restoring older code does not restore the protections added here.
